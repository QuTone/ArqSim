# ExecutionPlan Instruction Reference

Level 2 · Role: generated-instruction reference · Status: current for ArqSim 0.2.0

This document describes the current `arqsim.execution-plan.v9` contract. The
records below are generated by plan lowering. Ordinary users configure an
evaluation through `EvaluationConfig`; they do not hand-author these records.

## Mental model

An `ExecutionPlan` is the last fully offline artifact:

```text
ExecutionPlan
├── ProgramDAG                  finite application work
├── ResourceDAG                 recurrent supply/delivery templates
└── architectural_state        runtime inventory and t=0 bootstrap
    ├── buffers
    ├── engines                compatibility spelling; see below
    └── initial_locations

                         evaluate(plan)
                               |
                               v
                    mutable ArchitectureState
          tokens, slots, occupancy, users, locations, reservations
```

The Plan contains executable guards and state-transition rules, but not the
realized token identities, occupancy history, or timestamps. Program and
Resource work interact at runtime through the same mutable state. They do not
need fixed cross-DAG producer-instance-to-consumer edges.

## A logical layer is not an execution wave

`FTCircuit.layers` are conservative dependency antichains. For gate input,
Qiskit may place disjoint operations in the same layer. This proves that their
source dependencies permit overlap; it does not prove that a selected
architecture can execute them simultaneously.

The built-in v1 compiler currently forms work through this implicit sequence:

```text
LogicalLayer
  -> ComputePartition          compute-residency capacity
  -> ComputeBatch              magic-input capacity/policy
  -> CompiledComputeUnit       mapping, route, aggregate duration
  -> one EXECUTE_COMPUTE
```

Consequently, current `EXECUTE_COMPUTE` means one compiler-atomic compute
block. A block can contain one logical operation or several source operations.
Its `duration_s` is the compiler's aggregate block duration; the source layer
alone is never a timing proof. The current Plan lacks a typed compute-work
operand and stores the operation snapshot in `metadata.gates`. That historical
encoding is sufficient for the built-in, trusted, layer-preserving path, but it
is not the intended contract for a future general compiler exchange.

## Shared claim vocabulary

Program instructions and Resource processes share these flat fields:

| Field | Runtime meaning |
| --- | --- |
| `consumes` | Buffer ID to token quantity removed atomically at dispatch |
| `produces` | Buffer ID to output quantity reserved at dispatch and materialized at completion |
| `forwards` | Consumed-buffer ID to produced-buffer ID; preserves token identity across the move |
| `engines` | Compatibility spelling for capacity/contention claims, not operation location |
| `target_modules` | Semantic and visualization Module locus |
| `target_links` | Semantic and visualization Interconnect locus |

The word `engines` is broader here than an Architecture Profile `engine`
Submodule. The installed Plan inventory combines architecture-owned service
engines and synthesized contention domains:

| ID family | Meaning |
| --- | --- |
| `compute:<module>` | Compute-region service domain |
| `msf:<module>` | Architecture-owned magic-state factory engine |
| `bell_engine:<link>` | Architecture-owned logical-Bell producer engine |
| `program_move` | Synthesized Program movement concurrency budget |
| `store_load_buffer` | Synthesized Store/Load interface semaphore |
| `resource_move` | Synthesized resource-delivery concurrency budget |

Read an operation's `engines={id: amount}` as “claim this many units from this
contention domain while the event is active.” It does not answer where the
operation appears. Locus and state have separate authorities:

```text
target_modules / target_links             where the work belongs
required_locations / completion_locations where entities must be and move
engines                                    what concurrent capacity is claimed
```

The exact `engines` wire name is retained in Plan v9. A future schema should
replace this mixed abstraction with typed contention domains rather than apply
a cosmetic string rename.

## Program instruction fields

Every serialized `ArchitectureInstruction` has the common fields below.
Optional fields are emitted only when present.

| Field | Role | Notes |
| --- | --- | --- |
| `id` | DAG identity | Integer referenced by successors and Trace lineage |
| `opcode` | Discriminator | Must be a Program opcode |
| `predecessors` | Causal order | Earlier Program instruction IDs |
| `duration_s` | Planned service duration | Runtime realization resolves the candidate, then the execution timing backend finalizes its duration before commit |
| `layer` | Source lineage | Optional; current v1 lowerer also uses layers to preserve order |
| `qubits` | Direct logical-qubit payload | A summary for compute; exact entity set for movement/transfer work |
| `consumes`, `produces`, `forwards` | Buffer transition | Flat shared claims described above |
| `engines` | Capacity claim | Not a Module/link location |
| `required_locations` | Dispatch guard | Entity ID to required ArchitectureState location |
| `completion_locations` | Completion effect | Entity ID to resulting ArchitectureState location |
| `target_modules`, `target_links` | Locus | Trace/UI ownership; not a contention lock |
| `move_operands` | MOVE operand | Exact per-qubit source/destination slots for eager Program movement |
| `deferred_dispatch` | Late-binding request | Currently joint magic routing for Program compute |
| `implementation_recipes` | Conditional control | Finite resource-injection branch semantics |
| `continuation_templates` | Resolved child work | Pre-priced work activated by a selected recipe branch |
| `metadata` | Receipt | Compiler/timing diagnostics; `gates` is the current historical semantic exception |

Typed field names are reserved and are rejected if repeated inside `metadata`.
This prevents an opaque receipt from becoming a second execution authority.
`metadata.gates` is the single documented exception, and is accepted only on
`EXECUTE_COMPUTE` until v1.5 introduces typed compute work.

### Program opcode applicability

The table lists fields that are normally non-empty in plans generated by the
built-in lowerer. Common identity, dependency, duration, and empty-map fields
are omitted from the cells.

| Opcode | Logical payload and state | Capacity/resource claims | Locus and specialized fields |
| --- | --- | --- | --- |
| `EXECUTE_COMPUTE` | Operated `qubits`; all resident qubits normally appear in `required_locations`; no location completion | `compute:<module>`; magic/RZ work consumes its compute-side resource buffer | Compute Module; optional magic `deferred_dispatch`; optional finite recipes/templates; logical operations currently in `metadata.gates` |
| `MOVE_QUBITS` | Moved `qubits`; exact required and completion locations | `program_move` | Compute Module; required typed `move_operands` with exact slots |
| `TELEPORT_QUBITS` | Teleported `qubits`; source/destination endpoint locations | Consumes `bell:<link>` | Both endpoint Modules and the link; current Program path has no separate link-capacity claim |
| `STORE_QUBITS` | `qubits` is the outgoing wave; required endpoint location; no immediate completion move | `store_load_buffer` | Compute and memory Modules; Store syndrome-service receipt |
| `LOAD_QUBITS` | `qubits` is the incoming wave; required map includes incoming and outgoing waves; completion atomically swaps both | `store_load_buffer` | Compute and memory Modules; Load syndrome-service receipt |
| `CLASSICAL_REACTION` | No qubit/location payload in the current built-in T path | No contended classical engine today | Generated as runtime continuation work rather than a top-level source instruction |
| `FENCE` | No state transition | No claims | Zero-duration Program-order boundary |

`PREPARE_MAGIC_STATE` and `PREPARE_LOGICAL_BELL` are Resource-only opcodes.

## Finite gadget fields

`implementation_recipes` and `continuation_templates` are related, but they
are not interchangeable:

```text
InjectionRecipe                         ProgramWorkTemplate
-------------------------------         -------------------------------
which resource state is required        what selected child work executes
which measurement branch follows        resolved duration
next angle stage or correction           buffer/contention/location claims
logical parent/source identity           architectural locus

control-flow edges                       executable node bodies
```

The split keeps user configuration minimal and preserves one timing authority:
recipes contain no timing scalars; plan lowering resolves possible child work
from the selected latency/compiler authorities and freezes it in templates.
Runtime uses the recipe to choose a branch and the corresponding template to
materialize an event. A batched T block may also have one measurement work item
shared by several logical T invocations, so a template cannot simply be nested
inside one invocation recipe.

Finite T lowering accepts a pure T compute unit, including shared `T || T`, but
fails closed when the compiler aggregates Clifford work with T work in the
same unit. The compiler must split `H || T` and `CX || T` before lowering;
`black_box` mode does not impose this restriction.

The current two-list encoding nevertheless repeats several facts, including
source layer, qubits, compute locus/claim, stage indices, and correction
identity. Both lists are lowerer-generated Plan internals, not user-authored
gadget configuration. A future schema should expose one finite conditional
execution graph or one `RuntimeGadgetPlan` wrapper rather than extend these
parallel records.

## Resource process fields

Every `ResourceProcess` is a recurrent template. It has no Program predecessor
list, source layer, logical-qubit tuple, or logical-qubit location maps.

| Field | Runtime meaning |
| --- | --- |
| `id`, `opcode` | Stable process-template identity and Resource action |
| `consumes`, `produces`, `forwards`, `engines`, targets | Shared claims described above |
| `duration_s` | Deterministic service component |
| `arrival_distribution` | Optional sampled/replayed service interval; actual duration is sampled interval plus `duration_s` |
| `parallelism` | Maximum simultaneous instances of this same recurrent template |
| `dispatch_policy` | `single`, or `eager_available` batching of the currently feasible token quantity |
| `output_overflow_policy` | `block`, or `discard_excess` from a producer batch |
| `protocol` | Resource protocol identity used by provenance and resource fidelity |
| `deferred_dispatch` | Currently a state-bound Resource MOVE realization |
| `metadata` | Non-authoritative diagnostic receipt |

For Report-v1 and named system-case compatibility, current producer/delivery
records still repeat the derived receipt keys `outputs_per_batch` and
`consumes_one_logical_bell_pair`. Runtime never reads these keys: executable
quantities are owned by typed `produces` and `consumes` claims. Their removal
is intentionally deferred to the reviewed v1.5 Plan/report migration.

An arrival distribution records `kind`, `mean_interval_s`,
`success_probability`, `trace_intervals_s`, `repeat_trace`, `initial_delay_s`,
and `initial_delay_samples`. Supported kinds are `deterministic`,
`exponential`, `geometric`, and `trace`.

### Resource opcodes generated today

| Process/opcode | Token flow | Timing/concurrency | Locus and protocol |
| --- | --- | --- | --- |
| `prepare_magic` / `PREPARE_MAGIC_STATE` | Produces an MSF-output batch | Magic arrival distribution; MSF-copy parallelism; `msf:<module>` claim; discard excess | MSF Module; selected magic protocol |
| `prepare_logical_bell:<link>` / `PREPARE_LOGICAL_BELL` | Produces `bell:<link>` | Bell arrival distribution; Bell-copy parallelism; `bell_engine:<link>` claim; discard excess | Link; selected Bell protocol |
| `deliver_magic_local` / `MOVE_QUBITS` | Consumes MSF output, produces compute input, and forwards the same magic token | Local delivery duration; eager batching; `resource_move` claim | MSF and compute Modules; state-bound Resource MOVE recipe |
| `deliver_magic_remote` / `TELEPORT_QUBITS` | Consumes MSF output plus one Bell pair, forwards magic into compute input, destroys the Bell token | Link service duration; delivery-channel parallelism; `resource_move` claim | MSF and compute Modules plus link; logical magic teleportation protocol |

The Resource opcode vocabulary also permits `STORE_QUBITS` and `LOAD_QUBITS`,
but the built-in Resource lowerer does not currently generate them and there is
no canonical built-in field profile for those variants.

## Runtime state boundary

Plan `architectural_state` is inventory plus bootstrap, not a live snapshot:

- buffers declare capacity, slot IDs, token kind, owner, and optional initial
  contents;
- engines declare capacity and optional owner;
- `initial_locations` declares logical-qubit starting locations.

The canonical lowerer starts magic/Bell buffers empty and engine use at zero.
During execution, `ArchitectureState` adds ready tokens, pending outputs,
reserved slots, engine users, concrete token-slot bindings, current locations,
active reservations, and a state version. Dispatch and completion transitions
mutate that one state transactionally; immutable topology itself does not
change.

## Current boundary and planned cleanup

For the first release, the built-in compiler is intentionally described as a
conservative, layer-preserving reference compiler. Plan v9 remains a trusted
advanced artifact, not a general external-compiler submission contract.

Before a general compiler exchange is exposed, the instruction model needs:

1. a typed compute-work operand instead of `metadata.gates` authority;
2. explicit compiler-selected block formation and block critical-path timing;
3. opcode-specific sparse variants instead of one wide flat record;
4. a typed operation locus and typed contention domains;
5. one finite conditional-work graph for T and angle-doubling gadgets; and
6. stable source-operation IDs and exact dependencies for cross-layer action
   scheduling.
